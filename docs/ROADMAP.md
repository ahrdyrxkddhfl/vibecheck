# VibeCheck 로드맵

> 최종 갱신: 2026-08-24

## 이 도구가 푸는 문제

AI로 만든 코드를 본인도 설명하지 못하는 상황. 특히 면접이나 코드 리뷰에서
"이 함수 왜 이렇게 짰어요?"에 답하지 못하는 문제를 다룬다.

단순히 코드를 설명하는 도구가 아니라, **사용자가 자기 코드를 설명할 수 있게 만드는**
학습 도구를 지향한다. 이 방향이 리포트·면접질문·타자연습·학습진단을 하나로 묶는다.

## 현재 상태 (2026-08-24)

### 완료

- 코어 파이프라인: 수집 → tree-sitter 파싱 → 청킹 → LLM 요약(Haiku) → ChromaDB → Q&A(Sonnet)
- SHA-256 해시 기반 요약 캐싱 (외부 레포에서도 작동 확인)
- `Chunk.imports` 주입
- L1 파일 청크 (파일 개요를 검색 대상으로)
- `whyd index` / `whyd ask` CLI 동작
- 실험 B: 독스트링 제거 대조
- 실험 A / A2 / A3: 외부 레포(ctxd) Q&A 품질 측정

추가 파라미터 조정은 그 시험지에 대한 과적합이 된다.

## 방향 전환 — 로컬 웹앱

CLI만으로는 만들려는 것을 담을 수 없다. 로컬에서 도는 웹앱으로 간다.

**로컬 실행을 택한 이유**: 공개 서비스로 만들면 zip 업로드 보안(zip bomb, 경로 탈출),
인덱싱 대기 UX, API 키를 누가 부담하는가 문제가 한꺼번에 생긴다.
로컬이면 경로를 직접 받으므로 이 문제가 전부 사라진다.
공개 서비스는 필요해지면 그때 얹는다.

**CLI 출력 개선은 하지 않는다.** 마크다운 렌더링, HF 경고 억제, 근거 목록 배치는
전부 터미널 전용 문제이고 웹에서는 브라우저가 해결한다. 버려질 코드다.
단, **답변 길이 문제는 프롬프트 문제**이므로 웹에서도 남는다. 리포트 작업 중에 다룬다.

## 목표 기능

### 1. 리포트

코드를 넣으면 자동으로 생성되는 개요 문서. 웹앱의 첫 화면.

목차는 "면접에서 이 레포를 설명해야 한다면 뭘 알아야 하는가"에서 역산했다.

| # | 항목 | 대응하는 면접 질문 |
|---|---|---|
| 1 | 한 줄 정의 + 한 문단 개요 | "이거 뭐 하는 프로젝트예요?" |
| 2 | 규모 (파일·줄·심볼 수, 문서화 수준) | — |
| 3 | 외부 의존성과 용도 | "왜 이 라이브러리 썼어요?" |
| 4 | 모듈 지도 (파일별 한 줄 역할) | "구조 설명해보세요" / "이 기능 어디 있어요?" |
| 5 | 진입점 | "어디부터 실행돼요?" |
| 6 | **특이 지점** | "여기 좀 이상한데 왜 이래요?" |

**6번이 차별점이다.** 1~5는 `tree`와 README로도 대충 나오지만
6번은 코드를 읽어야만 나온다. ctxd 기준 예시:

- `save_secret_bundle`이 `base_url`을 받아놓고 첫 줄에서 버림
- 동기 `Client`가 비동기 `AsyncClient`를 감싸는 구조
- `SearchItem`이 `id`와 `document_uid`를 둘 다 받음
- API 키 우선순위가 SDK와 CLI에서 다름

### 2. 질문 답변 + 기록

이미 동작하는 `ask`에 기록 저장을 붙인다. 무엇을 언제 물었는지가 학습 진단의 재료가 된다.

### 3. 면접 예상질문 + 연습 모드

리포트를 재료로 예상 기술질문을 생성하고, 답변을 연습할 수 있게 한다.
**리포트 없이 만들면 매번 레포 전체를 훑어야 한다. 리포트 = 재료 준비, 면접질문 = 요리.**

**질문만 주고 답은 주지 않는다.** 답을 같이 주면 외우게 되는데,
이 도구의 목표는 사용자가 자기 코드를 설명할 수 있게 만드는 것이다.
답이 궁금하면 `ask`로 물어보게 한다.

다만 각 질문에 **답변 전략**은 붙인다.
어디까지가 코드로 답할 수 있는 부분이고 어디부터가 추측인지를 구분해준다.
실험 A/B에서 확인했듯 "왜"의 상당 부분은 코드에서 복원 불가능하므로,
사용자에게도 "복원 불가능한 것을 아는 척하지 않는 법"을 가르쳐야 한다.

#### 연습 모드 흐름 (웹)

```
1. 질문 제시
2. 사용자가 백지에서 답 작성
3. AI 피드백
4. "코드에서 확인하기" -> ask 결과 표시
5. 기록 저장
```

**주관식으로 하는 이유**: 재인(보기에서 고르기)과 회상(백지에서 말하기)은
다른 능력이다. OX나 객관식은 고를 수 있지만 말은 못 하는 상태를 만든다.
면접은 백지에서 말하는 자리다.

#### 채점 기준

정답 여부가 아니라 **면접에서 통할 답인지**로 본다.
"왜"의 정답은 코드에 없는 경우가 많아 내용 일치로는 채점할 수 없다.

| 볼 것 | 설명 |
|---|---|
| 구체적 근거 | 파일명·함수명·동작을 짚었는가 |
| **확신과 추측의 구분** | 코드에 없는 것을 단정하지 않았는가 |
| 코드를 읽은 흔적 | 일반론이 아니라 이 레포 얘기인가 |

두 번째가 핵심이다.
"확장성 때문입니다"는 위험하고, "확장성일 수도 있으나 코드에 근거는 없습니다"가 좋은 답이다.
후자는 오히려 코드를 제대로 읽었다는 증거가 된다.

**채점 재료는 `ask`가 제공한다.** 사용자 답변과 코드에서 뽑은 근거를 비교하면,
일반론이 아니라 이 레포의 코드에 붙은 피드백이 나온다.

### 4. 타자 연습

한컴타자연습처럼 코드를 따라 치되, 치는 동안 해당 함수의 설명이 화면에 떠 있다.
무작정 복붙하거나 따라 쳐도 뭔지 모르는 문제를 겨냥한다.

**재료는 이미 다 있다.** 청크 하나 = 연습 한 판.

| 필요한 것 | 출처 |
|---|---|
| 따라 칠 코드 | `Chunk.code` |
| 띄울 설명 | `Chunk.summary` |
| 위치 | `Chunk.file`, `start_line`, `end_line` |

**설계 판단**: 청크를 통째로 치게 하면 안 된다. `_build_parser`는 100줄이 넘는다.
화면 위에 함수 설명을 고정해두고 아래에서 **한 줄씩** 진행한다.
긴 청크(20줄 초과)는 건너뛸 수 있게 한다.

### 5. 학습 진단

질문 기록과 타자 기록을 합쳐 약한 영역을 짚어준다.

**신호 하나로는 부족하고 둘이면 가능해진다.**

- 질문 기록: 무엇을 반복해서 물었나
- 타자 기록: 어디서 자주 틀렸나(낯선 문법), 어디서 느려졌나(이해하며 멈춘 지점),
  어떤 청크를 반복해서 쳤나(어렵다고 느낀 곳)

## 작업 순서

```
1. L0 조립 부분          ✅
2. L0 요약               ✅
3. whyd report           ✅
4. 특이 지점 탐지         ✅ (규칙 1개: 미사용 인자)
5. whyd interview        ← 다음
6. 답변 채점 기능
7. 서비스 계층 정리 + SQLite (기록 저장)
8. FastAPI
9. 프론트엔드 (타자 연습, 면접 연습 모드 포함)
```

5~6은 웹 없이 만들고 CLI에서 검증한다.
답이 입력되고 피드백이 오가는 경험은 웹에서 완성되지만,
질문 생성과 채점 자체는 백엔드 기능이므로 화면을 기다릴 이유가 없다.

### 왜 L0가 먼저인가

리포트를 만들려면 레포 전체를 조망하는 정보가 필요한데 지금은 L2(함수)와 L1(파일)뿐이다.

**실험에서 Q01("이 프로젝트 뭐하는 거야?")이 정답 청크를 세 번 다 miss한 것이 이 때문이다.**
그 질문의 답은 어느 파일 하나가 아니라 전체에 흩어져 있다.
`_build_parser`가 운 좋게 걸려서 답이 나왔을 뿐, 구조적으로 답할 수단이 없었다.

### L0 구성과 생성 방식

| 필드 | 리포트 항목 | 생성 |
|---|---|---|
| 레포 요약 | 1 | **LLM 1회** (L1 요약들 종합) |
| 통계 | 2 | 조립 |
| 외부 의존성 | 3 | 조립 (L1 imports에서 내부/외부 분리) |
| 파일별 역할 | 4 | 조립 (L1 요약 나열) |
| 진입점 후보 | 5 | 조립 (`__main__`, `cli`, `main` 탐지) |
| 특이 지점 | 6 | **LLM 별도 호출** |

**L1과 달리 L0에는 LLM을 쓴다.** L1은 검색용이라 키워드만 있으면 됐지만
L0는 사람이 읽는 리포트용이라 문장이 필요하다.
비용은 레포당 Haiku 2회로 미미하다.

**특이 지점 탐지는 난이도가 다르다.** "이상한 데 찾아봐"는 열린 질문이라
LLM이 헛것을 볼 위험이 크다. 프롬프트를 여러 번 다듬어야 할 것으로 예상하고
나머지가 다 돌아가는 상태에서 집중해서 만든다.

### SQLite 스키마 설계 시 주의

질문 기록만 생각하고 설계하면 안 된다.
**타자 연습 기록 테이블을 처음부터 함께 넣는다.** 나중에 붙이면 스키마를 다시 고치게 된다.

## 미해결 / 보류

- **Q14 (URL 정규화)**: 세 조건 모두 실패. `base_url`이라는 이름을 공유하는 청크가 많아
  정작 정규화를 수행하는 `_normalize_base_url`이 밀린다.
  사례가 하나뿐이라 단정하지 않고, 실사용에서 유사 사례가 쌓이면 패턴으로 다룬다.
- **`__init__.py`가 인덱싱되지 않음**: 함수·클래스가 없어 청크가 0개가 되고 L1도 생성되지 않는다.
  패키지 공개 API 정보가 검색 대상에서 빠진다. L0가 이를 일부 보완할 수 있다.
- **답변 길이**: 한 줄짜리 질문에 화면 한 판이 나온다. 프롬프트 문제이므로 웹에서도 남는다.
  다만 A3에서 23점을 받은 프롬프트이므로 손대면 재측정이 필요하다.
- **실험 C (README 인덱싱)**: 문서를 함께 넣으면 "왜"가 복원되는가.
  현재 `.py`만 수집하므로 기능 추가가 필요하다.
- **BYOK**: 공개 서비스로 갈 경우에만 필요.
- **특이 지점 규칙이 하나뿐**: 미사용 인자만 탐지한다. 나머지 셋(비슷한 함수 쌍,
  한 개념 두 이름, 감싸는 구조)은 interview를 만들어보고 재료가 부족하면 추가한다.
  먼저 만들면 면접 질문에 쓰이지 않는 규칙을 만들 위험이 있다.

## 축적된 원칙

- **프롬프트의 금지 규칙에는 반드시 허용 규칙을 짝지운다.** 한쪽만 쌓이면 과잉 억제가 일어난다.
  (`Chunk.imports` 때 "라이브러리명 추측 금지"가, 답변 프롬프트에서 "근거 없으면 기권"이 같은 문제를 냈다.)
- **진단이 "도달 실패"라면 정보를 늘리기 전에 통로부터 넓힌다.**
  L1 도입(+1)보다 top_k 조정(+2)이 나았다. top_k는 공짜이고 되돌리기 쉽다.
- **검색 순위와 답변 품질은 독립적으로 움직인다.** 순위가 떨어져도 점수가 오르고,
  순위가 올라도 점수가 그대로인 사례가 모두 관찰됐다. 검색 지표만으로 도구 품질을 판단할 수 없다.
- **계층을 추가하면 top_k도 함께 조정해야 한다.** 청크가 늘면 기존 청크가 밀려난다.
- **제외 규칙은 대체가 아니라 합집합이어야 한다.** 대체를 허용하면 `.venv` 방어선이 조용히 풀린다.
- **한 번에 하나만 바꾼다.** 두 가지를 동시에 바꾸면 어느 쪽 효과인지 알 수 없다.
- **같은 시험지로 반복 측정하며 튜닝하면 과적합이다.** 개선되는 것은 도구가 아니라 그 시험지의 점수다.
- **interview 질문 중복**: ctxd에서 Q9와 Q10이 동일하게 생성된다.
  Q6은 심볼 목록이 `mock_post, mock_post, mock_post`처럼 같은 이름을 반복한다.
  quirks.py의 group_quirks가 이름만으로 묶어 파일이 다른 동명 함수를
  하나로 뭉갠 것으로 보인다. SQLite 저장 후 DB를 조회하며 발견했다.
