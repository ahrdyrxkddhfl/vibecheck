# Java 지원

내 프로젝트의 절반이 Java인데 이 도구는 파이썬만 읽었다. MSA 강의 레포를 돌렸을 때
Java 파일이 조용히 전부 빠졌던 것이 이 도구의 첫 실사용 한계였다.
대상 레포는 직접 만든 Spring 프로젝트 claim-trace(Java 79개, 파이썬 0개)다.

## 범위

질의응답, 면접 질문, 채점까지 지원하고 호출 관계(관계도)는 파이썬 전용으로 둔다.

호출 그래프의 해석 규칙(callgraph.py)은 파이썬 import 방식에 맞춰져 있다. Java는
오버로딩과 인터페이스 주입이 흔해 이름만으로는 어느 구현을 부르는지 좁혀지지
않는다. 틀린 화살표를 그리느니 그리지 않고, 화면에서 "분석하지 않는다"고 말한다.

## 순서: 구조를 먼저 옮기고 기능을 얹었다

언어마다 다른 것을 `core/languages.py`의 언어 설정 하나로 모으는 리팩터링을 먼저
하고, 그 위에 Java를 얹었다. 둘을 한 번에 하면 무엇이 깨졌을 때 어느 쪽 탓인지
가를 수 없다.

리팩터링이 동작을 바꾸지 않았는지는 인덱싱 결과로 확인했다. 요약만 고정 문자열로
바꾼 가짜 클라이언트로 실제 `index_repo`를 돌려(요금 없음) 청크마다 id, 종류, 줄
범위, import, 호출, 파일 요약, 본문 지문을 떴다. 대상은 세 파이썬 레포다.

- vibecheck: 리팩터링 전 커밋을 얼려둔 사본. 도구가 자기 코드를 고치므로 레포를
  그대로 재면 결과가 바뀌는 것이 당연하다. 도구는 바뀌고 대상은 그대로여야 한다.
- mfds-drug-pipeline, ctxd: 다른 코드 습관을 가진 레포.

| 레포 | 청크 | 호출 | 리팩터링 후 | Java 추가 후 |
|---|---|---|---|---|
| vibecheck(사본) | 191 | 183 | 같음 | 같음 |
| mfds-drug-pipeline | 66 | 57 | 같음 | 같음 |
| ctxd | 72 | 60 | 같음 | 같음 |

가짜 요약으로 뜬 vibecheck 사본의 청크 191개, 호출 183건은 같은 날 실제로
`whyd index`를 돌린 숫자와 같았다. 가짜 클라이언트가 인덱싱 흐름을 흐리지 않는다.

## Java에서 처음 알게 된 것

노드 이름은 추측으로 짜지 않고 claim-trace 79개 파일을 파싱해 확인했다.
문법 오류는 0개였다.

**Javadoc은 선언 밖에 있다.** 파이썬 독스트링은 함수 본문 안이라 줄 범위로 자르면
딸려 오지만, Javadoc은 선언 앞의 별도 노드다. 본체 코드에서 선언 230개가 전부
바로 윗줄에 Javadoc을 달고 있었다. 선언 범위만 자르면 작성자가 쓴 설명이 청크에서
통째로 빠진다. `walk`가 바로 앞에 붙은 문서 주석까지 범위에 넣게 했고, 최상위
타입의 Javadoc은 파일 설명으로 쓴다. 모듈 지도에 파일마다 Javadoc 첫 문장이 붙은
것이 그 결과다.

**같은 파일에 같은 이름이 생긴다.** 오버로딩 때문이다. claim-trace에서는 두
건이었다(`ReviewResponse.from`, `InvariantViolationException` 생성자). 청크 id가
"파일::심볼"이라 겹치면 하나가 사라진다. 두 번째부터 `#2`, `#3`을 붙인다. 파이썬의
property getter·setter도 같은 경우인데, 세 파이썬 레포에는 겹침이 없어 결과가
바뀌지 않았다.

**import 첫 조각은 Java에서 뜻이 없다.** 외부 의존성이 `jakarta`, `java`, `lombok`,
`org`, `tools`로 나왔고, 면접 질문이 이 목록으로 "`java`, `org`는 각각 어디에
쓰이나요?"를 물었다. 개요는 범위 밖으로 뒀지만 범위 안의 면접 질문을 망가뜨렸다.
Java는 패키지 앞 두 조각으로 묶고 `java.`, `javax.`는 표준으로 뺀다. 결과는
`org.springframework`, `tools.jackson`, `jakarta.persistence` 등 열 개다.

## 파이썬 쪽이 바뀌지 않았다는 확인

채점의 파일 개요는 파일 설명을 파이썬 `ast.get_docstring`으로 꺼내다가, 인덱싱
때와 같은 언어별 함수로 꺼내게 바꿨다. 세 레포 파이썬 파일 78개에서 두 방식이
꺼낸 설명이 모두 같았다.

외부 의존성과 진입점 판단을 언어 설정으로 옮긴 뒤에는, 같은 인덱스를 옛 코드(얼린
사본)와 새 코드로 각각 읽어 개요를 비교했다. vibecheck와 ctxd 모두 의존성, 표준
라이브러리, 내부 참조, 파일 간 연결, 진입점, 모듈 지도가 같았다.

## Java에서 되는 것과 안 되는 것

- 인덱싱: 청크 453개(클래스 93, 메서드 269, 파일 79, 문서 12), 요약 362개.
- 채점: README 근거로 주장 하나를 확인, 하나를 모순으로 갈랐다. 한 판이다.
  답변이 `.java` 파일을 짚을 때 근거로 가져오는 것은 테스트로만 확인했다.
- 호출 관계: 만들지 않는다. 관계도는 함수 목록만 보여준다.
- 설계 결정 질문: 나오지 않는다. 특이 지점을 찾는 `quirks.py`가 파이썬 `ast`로
  짜여 있어 Java 파일을 건너뛴다. 면접 질문의 나머지는 나온다.

## 남은 것

- 레포 자기 패키지의 static import나 와일드카드 import는 파일 이름과 대조되지 않아
  외부 의존성으로 잘못 올라갈 수 있다. claim-trace에서는 0건이었다.
- 진입점 안내가 Java 레포에서도 "pyproject.toml에 등록된 명령이 없습니다"로 시작했다.
  "확정할 수 있는 진입점이 없습니다"로 바꿨다.
- claim-trace는 처음으로 청크가 수백 개인 레포였고, 요약하는 몇 분 동안 진행 표시가
  없었으며 중간에 끊으면 요약 캐시가 하나도 저장되지 않았다. 둘 다 고쳤고 요약을
  동시에 보내게도 했다. [`indexing_resume_and_speed.md`](indexing_resume_and_speed.md) 참고.
- 채점이 답변의 `.java` 경로뿐 아니라 확장자 없는 클래스 이름으로도 파일을 근거로
  가져오게 했다. 공개 클래스 이름이 파일 이름이라는 Java 규칙에 기댄다.
