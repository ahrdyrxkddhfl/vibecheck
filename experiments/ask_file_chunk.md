# whyd ask에 들어가는 파일 청크 원문

채점 경로는 파일 청크를 개요와 호출 목록으로 줄였다(`compact_file_chunk`,
`grading_mentioned_files.md` 참고). 질의응답에도 같은 원문이 들어가는지,
들어간다면 같은 방식으로 줄여도 되는지 쟀다.

## 재정렬이 걸러주는가

`ask`는 후보 32개 중 8개를 LLM 재정렬로 고르므로, `KIND_QUOTAS`가 파일 청크
두 자리를 떼어둬도 최종 근거에 남는다는 보장은 없다. 재정렬까지 실제로 돌리고
답변 생성 호출만 가로채 메시지를 쟀다.

| 질문 | 파일 청크 | 원문 토큰 | 개요 토큰 |
|---|---|---|---|
| 파일들이 서로 어떻게 얽혀 있나요? 의존 방향을 설명해보세요. | 3 | 21,380 | 8,816 |
| 어떤 벡터 DB를 쓰나요? | 1 | 12,137 | 8,817 |
| 코드를 어떻게 파싱하나요? | 2 | 19,601 | 7,132 |
| 채점은 어떻게 이루어지나요? | 0 | 7,354 | 7,354 |
| 파일 수집은 어떻게 이루어지나요? | 1 | 12,391 | 7,191 |
| 합계 | | 72,863 | 39,310 |

다섯 질문 중 넷에서 파일 청크가 최종 근거에 남았다. 재정렬은 거르지 않는다.

원문의 상당 부분은 중복이다. 벡터 DB 질문은 `VectorStore` 클래스와 메서드 넷이
이미 근거에 있는데 `vector.py` 원문이 한 번 더 들어간다. 파일 수집 질문도
`collector.py`의 함수 넷 위에 원문이 겹친다.

## 개요로 바꾸면 답이 얕아지는가

재정렬은 질문당 한 번만 하고, 같은 근거로 원문과 개요 두 가지 답변을 만들었다.
두 답변에서 다른 것은 파일 청크의 모양뿐이다. 질문당 한 판씩이다.

**의존 방향 질문.** 개요 쪽이 떨어지지 않았다. 호출 목록 덕분에 `build_overview`가
`collector.py`의 함수들을 부른다는 것, LLM을 부르는 것은 `summarize_repo`뿐이라는
것처럼 원문 답변에 없던 사실이 들어갔다. 원문 답변은 도식에서 `collector.py`가
`Chunk` 모델을 쓴다고 그려놓고 본문에서는 표준 라이브러리만 쓴다고 해, 같은 답변
안에서 모순됐다. 한 판이라 이 차이가 원문 때문이라고 단정하지는 않는다.

**파싱 질문.** 개요 쪽이 얕아졌다. 행 번호 +1 보정, 부모 이름을 자식에게 물려주는
소속 추적 방식, `obj.foo()`는 수신자를 기록하고 `a.b.c()`는 기록하지 않는 규칙이
빠졌다. 셋 다 `walk`와 `collect_calls`의 본문에 있는데, 이 둘은 따로 근거에 들지
못했고 `parser.py` 원문을 통해서만 들어왔다.

## 판단

`ask`에는 적용하지 않는다.

채점과 질의응답은 파일 청크에 바라는 것이 다르다. 채점은 답변의 주장이 맞는지
대조하면 되므로 무엇이 무엇을 부르는지만 있으면 됐다. 질의응답은 "어떻게"를
설명해야 하고, 그 답이 근거에 따로 들지 못한 함수의 본문에 있을 때 원문이
유일한 통로가 된다. 입력이 절반으로 줄어드는 대신 이 도구가 하려는 설명이
얕아진다.

같은 이유로 `load_chunks`가 파일 청크를 원문으로 복원하는 것을 일괄로 고칠
결함으로 보지 않는다. 쓰는 쪽마다 필요한 모양이 다르므로, 줄일 필요가 있는
쪽에서 줄인다.

## 남은 것

- 중복은 줄일 여지가 있다. 같은 파일의 심볼 청크가 이미 근거에 있으면 원문에서
  그 부분은 새 정보가 아니다. 다만 파싱 질문처럼 근거에 없는 함수가 원문의
  값이므로, 통째로 빼지 말고 겹치는 심볼만 덜어내는 방식이어야 한다. 재지 않았다.
- 비교는 질문당 한 판이다. 답변 생성은 판마다 달라지므로 적용 여부를 다시
  따질 일이 생기면 판 수를 늘려야 한다.
