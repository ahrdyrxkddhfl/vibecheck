# 식별자 검색이 벡터로는 안 된다

측정일: 2026-08-28
대상: vibecheck 자기 자신 (청크 197개, top_k 기본 8)
코드 변경 없음. 인덱스를 읽기만 했다.

## 발단

`whyd practice` Q2에서 근거 8개에 `cli.py::main`이 없었다.
진입점을 묻는 질문에 진입점 함수가 안 온 것이다.

## 측정 1 — main이 몇 등인가

질의 `콘솔 스크립트 진입점`. 이 문장은 `main`의 독스트링 그대로다.

- `main` **69등**, 거리 0.8629 (1등 0.6814)
- 청크는 인덱스에 정상 존재. 청킹 문제가 아니다.

임베딩 텍스트를 조각내 각각 질의와의 거리를 쟀다.

| 조각 | 거리 |
|---|---|
| 전체 (지금 방식) | 0.8629 |
| 머리말 뺌 (요약+코드) | 0.8549 |
| 요약만 | 0.8206 |
| 코드만 | 0.8612 |
| 머리말만 | 0.7770 |

최선이 0.7770으로 1등 0.6814에 못 미친다.
**`build_embedding_text`를 어떻게 조합해도 이 청크는 상위에 못 온다.**

"코드만"이 0.8612인 것이 핵심이다. 코드 안에 질의 문장이 글자 그대로
들어 있는데도 가까워지지 않는다.

## 측정 2 — 식별자로 확인

질의 `child_by_field_name`. tree-sitter API로 `parser.py`에서만 쓴다.
이 낱말을 code에 담은 청크 6개의 순위:

| 순위 | 청크 |
|---|---|
| 4 | `vector.py::build_embedding_text` |
| 18 | `parser.py::walk` |
| 35 | `parser.py::extract_imports` |
| 118 | `parser.py` (파일 청크) |
| 126 | `parser.py::extract_imports.scan` |
| 133 | `vector.py` (파일 청크) |

**`top_k=8` 안에 실제 사용처가 하나도 없다.**
4등은 사용처가 아니라 독스트링에 예시로 이름을 적어둔 자리다.
문장 속 언급이 실제 사용처를 이겼다.

## 결론

`build_embedding_text` 독스트링에 적힌 근거가 사실이 아니다.

> 'child_by_field_name 쓰는 데 어디야?' 같은 식별자 질문은 코드 원문이 받아낸다.

코드 원문을 넣어도 식별자 질문을 받아내지 못한다.
`paraphrase-multilingual-MiniLM-L12-v2`는 문장 뜻을 재는 모델이라
희귀 식별자를 하나의 단위로 보지 않는다. 모델을 바꿔도 정도의 문제다.

대신 코드 원문은 청크마다 `def`, `self`, `return`이 반복되는 텍스트를
넣어 벡터를 서로 닮게 만든다. 상위 5개 거리가 0.68~0.75에 몰려 있다.

**검색에 경로가 하나 더 필요하다.** 식별자는 문자열로 찾고 자연어는
벡터로 찾아 합친다. 채점 검색을 질문·답변 합집합으로 바꾼 것과 구조가 같다.

## 다음

측정 세트를 먼저 고정한다. 식별자 질문 몇 개와 각각의 정답 청크를
정해 지금 순위를 기록해두지 않으면, 고친 뒤 나아졌는지 말할 수 없다.

## 기준선 (2026-08-31)

`scripts/measure_retrieval.py --v3`. 청크 164개, 재정렬 전 벡터 순위.

| 질의 | 1등 (거리) | 기대 | 순위 | 거리 |
|---|---|---|---|---|
| `child_by_field_name` | `collect_used_names` (0.5299) | `walk` | 19 | 0.7106 |
| | | `extract_imports.scan` | 130 | 0.8838 |
| `콘솔 스크립트 진입점` | `format_symbol_lines` (0.6814) | `main` | 70 | 0.8629 |
| `prune은 언제 호출되나요?` | `now` (0.6937) | `VectorStore.prune` | 2 | 0.7574 |
| `요약을 캐시할 때 왜 해시를 쓰나요?` | `summarize_repo` (0.3532) | `Manifest.apply` | 3 | 0.4925 |

네 질의는 유형별로 하나씩 골랐다. 순수 식별자, 독스트링 원문 그대로의
자연어, 식별자가 섞인 자연어, 그리고 대조군이다. 마지막 항목은 v2
시험지에서 그대로 가져왔다. 하이브리드가 식별자를 살리면서 자연어를
해치면 순이득이 아니고, 그 손실은 이미 잘 되던 질의에서만 보인다.

8월 28일 측정과 순위가 한 칸씩만 다르고 거리는 같다. 그 사이 청크가
197개에서 164개로 줄었으나(scripts 제외, README 절 추가) 결과는 그대로다.

식별자만으로 된 질의의 1등 `collect_used_names`는 그 API를 실제로
호출하는 `walk`보다 가깝다. 이름에 `names`가 들어가 어휘가 겹쳤을 뿐
관계가 없는 함수다.

`prune은 언제 호출되나요?`가 2등인 것이 범위를 좁혀준다.
식별자가 문장에 섞이면 문장 쪽이 검색을 이끌어 지금도 닿는다.
고쳐야 할 것은 식별자만으로 된 질의다.

뒤의 두 항목은 대조군이다. 하이브리드가 자연어 경로를 해치면
여기서 순위가 내려간다.

시험지 안에 성격이 다른 두 문제가 있다. `child_by_field_name`은
식별자 질의가 벡터로 안 되는 문제이고 문자열 매칭으로 덮인다.
`콘솔 스크립트 진입점`은 다르다. 질의가 식별자가 아니라 한국어
구절이고, 그 구절이 `main`의 독스트링에 그대로 있는데도 70등이다.
문자열 경로를 붙여도 이 질의는 그 경로를 타지 않아 그대로 남는다.

하이브리드로 고쳐지는 것은 앞의 하나다. 뒤의 것은 짧은 한국어
질의를 임베딩이 제대로 재지 못하는 별개의 문제로 남겨둔다.

## 하이브리드 도입 (2026-08-31)

`qa.py`에 `extract_identifiers`와 `search_by_identifier`를 넣고
`search_by_kind` 앞자리에 문자열 결과를 먼저 담게 했다.

질의에서 식별자로 보이는 낱말만 뽑아 문자열로 찾는다. 밑줄이나
대소문자 혼용을 요구해 `어디서`, `authentication` 같은 평범한
낱말을 걸러낸다. 모든 낱말을 문자열로 찾으면 자연어 질의에서
무관한 청크가 앞자리를 먹는다.

처음에는 질의 **전체**가 식별자일 때만 열었다(`is_identifier_query`).
`child_by_field_name`처럼 단어만 던지면 잘 됐으나
`child_by_field_name 어디서 써?`로 물으면 공백 때문에 경로가 열리지
않았고, 사용처 셋 중 하나만 걸려 답변이 "한 번 사용됩니다"로 나왔다.
실제 사용자는 단어만 던지지 않으므로 낱말 단위 추출로 바꿨다.
`is_identifier_query`는 쓰지 않으나 되돌릴 여지로 남겨두었다.

### 파일 청크를 뺀 이유

처음에는 종류를 가리지 않고 등장 횟수로 줄을 세웠다. `top_k`로
재보니 1·2등이 `qa.py`와 `practice.py` 파일 청크였고 정의부인
`VectorStore.search`가 5등이었다. 파일 청크는 파일 전체를 담아
등장 횟수가 구조적으로 높다. 흔한 이름일수록 이 편향이 커진다.
파일 청크는 벡터 경로로도 잡히므로 문자열 경로에서는 제외했다.

`child_by_field_name`에서도 같은 일이 있었다. 파일 청크를 빼기
전에는 `parser.py` 파일 청크가 1등이라 세 자리 중 하나를 먹었고
`walk`가 잘려나갔다. 빼고 나니 `walk`가 3등으로 들어왔다.

### 결과

| 질의 | 상위 3개 | 판정 |
|---|---|---|
| `build_embedding_text` | `build_embedding_text`, `VectorStore`, `VectorStore.add` | 정의부 1등 |
| `start_byte` | `walk`, `extract_imports`, `extract_imports.text` | 실사용처 독점 |
| `child_by_field_name` | `extract_imports`, `extract_imports.scan`, `walk` | 실사용처 독점 |
| `top_k` | `rerank`, `search_union`, `ask` | 파일 청크 제거로 해결 |
| `KIND_QUOTAS` | `rerank`, `Quirk`, `QuirkGroup` | 어긋남 |

기준선과 견주면 `extract_imports.scan`이 130등에서 2등,
`walk`가 19등에서 3등이다.

`KIND_QUOTAS`는 사용처가 적어 문자열이 세 자리를 다 채우지 못했다.
남은 자리를 벡터가 메우면서 `Quirk`, `QuirkGroup`처럼 이름만 닮은
것이 올라왔다. 실사용처 `search_by_kind`는 4등이라 top_k=8 안에는
든다. 벡터가 채우는 자리를 손대려면 자연어 경로를 건드려야 하므로
남겨둔다.

v2 시험지는 6/6을 유지했다. 자연어 질의에서는 문자열 경로가 열리지
않아 동작이 그대로다.

`콘솔 스크립트 진입점`은 이 변경으로 달라지지 않는다. 질의가
식별자가 아니라 문자열 경로를 타지 않는다. 앞서 갈라둔 별개 문제다.

### 자연어 경로 재확인

낱말 단위로 바꾸면 발동 범위가 넓어진다. v2 여섯 질문에서 실제로
뽑히는 것을 확인했다. `index_access`와 `group_quirks` 둘뿐이고
나머지 넷은 아무것도 뽑히지 않는다. `parser.py`, `records.py`는
소문자에 밑줄이 없어 걸리지 않는다. 걸린 두 질문은 모두 1등으로
통과했다.

v2는 두 번 돌려 6/6이 유지되는 것을 확인했다. 다만 순위는 흔들린다.
`인덱싱한 뒤에 코드를 수정하면 어떻게 되나요?`가 세 번의 측정에서
[2,3], [3,4], [1,2]로 나왔다. 재정렬이 LLM이라 생기는 변동이며
하이브리드와 무관하다. 검색 순위도 채점 점수처럼 1~2등 차이는
신호로 읽으면 안 된다.


### 적용 범위

`whyd ask`만 이 경로를 탄다. 채점은 `practice.search_union`이
`store.search`를 직접 불러 `search_by_kind`를 거치지 않는다.
이 조사의 발단이 practice Q2였으나 그쪽에는 아직 닿지 않는다.

지금 잇지 않는 이유는 채점이 근거 수에 민감하기 때문이다.
점수 변동폭이 ±1이라 근거 구성이 바뀌면 기존 측정과 비교할 수
없게 된다. 채점 질문은 대부분 자연어 문장이라 식별자 판정을
통과하지도 않아 당장 얻는 것도 적다. 채점 측정을 새로 돌릴
준비가 된 뒤에 잇는다.
