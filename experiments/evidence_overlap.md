# 근거 목록에 같은 코드가 두 번 실리던 문제

claim-trace 채점 근거에 `RuleEvaluator`가 파일 청크(1–326행)와 클래스 청크(18–326행)로
두 번 들어간 것을 보고, 한 번 있었던 일인지 늘 그런지를 쟀다.

## 무엇을 중복으로 보는가

같은 파일에서 한 청크의 줄 범위가 다른 청크의 줄 범위 안에 통째로 들어가면, 안쪽 코드는
근거에 두 번 실린 것이다. 클래스와 그 메서드, 파일 원문과 그 안의 함수가 이 경우다.

채점은 파일 청크를 개요로 줄여 보낸다(`compact_file_chunk`). 그래서 채점 쪽 파일 청크는
코드를 담지 않은 것으로 친다. `ask`는 파일 청크가 원문이라 담은 것으로 친다. 문서와 설정
청크는 범위가 겹쳐도 코드 중복이 아니다.

## 잰 것

파이썬(이 레포)과 Java(claim-trace)에서 질문 네 개, 채점과 ask를 합쳐 근거 목록 여섯 개다.
채점 근거는 검색만 하므로 요금이 없고, ask는 재정렬까지 실제로 돌리고 답변 생성만 가로챘다.

| 경우 | 채점 | ask |
|---|---|---|
| 파이썬, 의존 방향 | 0칸 | **3칸** (글자 28%) |
| 파이썬, 파싱 | – | 0칸 |
| Java, 개입 규칙 평가 | **2칸** (8%) | **4칸** (31%) |
| Java, 근거 채택·기각 | – | 0칸 |

여섯 번 중 세 번 겹침이 생겼고, 생기면 근거 8칸 중 2~4칸이었다. 모양은 늘 같았다. 큰 청크와
그 안의 메서드가 함께 뽑힌다. Java 개입 규칙 ask는 `RuleEvaluator` 클래스 안에 메서드 셋이,
테스트 파일 원문 안에 테스트 클래스가 다시 들어 있어 서로 다른 근거가 4개뿐이었다.

글자 비율보다 칸 수가 문제다. 근거 수는 8로 고정했다. 근거 수가 바뀌면 같은 답변의 채점
점수가 달라지는 것을 확인해 정한 값이라, 중복 칸은 다른 근거가 들어갈 자리를 빼앗는다.

## 어느 쪽을 남기나

- 담는 쪽(클래스, 파일 원문)을 남기고 안쪽을 뺀다. 안쪽 코드를 이미 담고 있어 잃는 정보가
  없다. 빈 칸을 새 근거로 채우므로 글자 수는 줄지 않는다.
- 안쪽을 남기고 담는 쪽을 뺀다. 글자 수는 줄지만 담는 쪽에만 있던 코드(뽑히지 않은 다른
  메서드, 필드)를 잃는다. ask에서 파일 원문을 줄였을 때 설명이 얕아지는 것을 이미 봤다
  (`ask_file_chunk.md`).

모자란 것은 칸이므로 담는 쪽을 남겼다. 담는 쪽이 뒤에 뽑혔으면 안쪽들 중 가장 앞 자리에
넣는다. 앞에 둔 것은 관련이 깊다고 고른 것이라 맨 뒤로 보내면 그 판단을 뒤집게 된다.

## 빈 칸을 어떻게 채우나

채점은 검색 결과를 하나씩 담을 때 이미 담은 것 안에 있으면 건너뛰고, 새것이 이미 담은
것을 품으면 그것을 빼고 다음 후보로 채운다. 질문 몫과 전체 칸을 채울 수 있게 검색은
넉넉히 한다.

ask는 처음에 재정렬에게 8개 대신 12개를 고르게 하고 겹침을 뺀 뒤 8개로 잘랐다. 여유분 4는
측정에서 본 최대 중복 칸 수였다. 그런데 Java 개입 규칙에서 **4칸만 남았다**. 재정렬이 두
파일 안에서만 골라, 더 고른 네 개까지 같은 클래스의 메서드라 겹침으로 함께 빠졌다. 더
고르게 하면 겹치는 것도 함께 늘어난다는 것을 놓쳤다. 겹침을 뺀 뒤에도 모자라면 재정렬이
고르지 않은 후보를 검색 순서대로 이어 채우게 고쳤다(`pick_distinct`).

## 고친 뒤

| 경우 | 채점 | ask |
|---|---|---|
| 파이썬, 의존 방향 | 8칸, 0칸 중복 | 8칸, 0칸 중복 |
| 파이썬, 파싱 | – | 8칸, 0칸 중복 |
| Java, 개입 규칙 평가 | 8칸, 0칸 중복 | 8칸, 0칸 중복 |
| Java, 근거 채택·기각 | – | 8칸, 0칸 중복 |

빈 칸에 들어온 것은 대체로 질문에 맞았다. 파이썬 의존 방향 ask에는 `build_module_map`,
`build_file_map`, README "어떻게 동작하나"가, Java 채점에는 README "6. 개입 규칙 — 조건을
코드가 아니라 데이터에 둔다"가 들어왔다. Java 채점의 `EvidenceCreateRequest`처럼 관련이 약한
것도 하나 있었다.

Java 개입 규칙 ask의 글자 수는 27,426자에서 27,071자로 거의 같았다. 담는 쪽을 남기고 빈
칸을 새 근거로 채웠으므로 예상한 대로다. 같은 분량에 담긴 서로 다른 코드가 4개에서 8개로
늘었다.

같은 답변의 claim-trace 채점은 고치기 전 4/6, 고친 뒤 세 판에서 3/6, 4/6, 4/6이었다. 세 판
모두 두 주장이 확인됨이었고, 3/6은 "판단보정" 한 축만 2에서 1로 내려간 것이다. 이 축은 근거
없이 단정했는지를 보므로 두 주장이 모두 확인된 답변에서 근거 목록 때문에 바뀔 이유가 없다.
채점기의 판마다 흔들림으로 본다.

## 주의

- 파이썬 쪽 고친 뒤 측정은 `qa.py`와 `practice.py`를 막 바꾼 상태라 두 파일의 청크 23개가
  인덱싱 뒤 바뀐 것으로 빠진 채 쟀다. 겹침을 보는 데는 상관없지만 근거 목록이 고치기 전과
  완전히 같은 후보에서 뽑힌 것은 아니다.
- 질문 네 개다. 겹침이 생기는 빈도(여섯 번 중 세 번)는 이 표본의 값이다.
