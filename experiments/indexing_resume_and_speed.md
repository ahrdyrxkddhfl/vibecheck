# 인덱싱을 끊어도 이어서 하고, 요약을 동시에 보낸다

claim-trace(Java 79개 파일, 요약할 청크 362개)는 처음으로 청크가 수백 개인 레포였다.
작은 레포에서는 보이지 않던 세 가지가 드러났다.

- 요약하는 몇 분 동안 아무것도 찍히지 않아 멈춘 것처럼 보였다.
- 요약 캐시를 인덱싱 끝에 한 번만 저장해, 도중에 끊으면 이미 요금을 낸 요약이 전부 사라졌다.
- 요약을 하나씩 순서대로 보내 느렸다. `summarize_all`에는 "실제 병목이 확인된 뒤에
  병렬화한다"고 적혀 있었는데, 이것이 그 확인이다.

## 중간 저장: 장부의 두 가지 일을 나눴다

파일 하나를 끝낼 때마다 장부를 저장하면 될 것 같지만 그렇게 하면 안 된다. 장부는
요약 캐시이면서, 지금 벡터 저장소의 청크가 어떤 해시의 파일로 만들어졌는지의
기록이다. `index_access.changed_files`가 이 기록으로 인덱싱 뒤 바뀐 파일을 가려낸다.

파일을 고치고 인덱싱하다 끊기면, 도중의 저장이 새 해시를 기록에 적는다. 벡터
저장소에는 옛 청크가 남아 있는데 장부는 바뀌지 않은 파일이라고 말하게 되고, 옛 줄
범위로 새 파일을 읽는다. 인덱싱 뒤 줄이 밀린 파일을 조용히 잘못 보여주던 버그가
되살아나는 길이다.

그래서 도중의 요약은 장부의 `pending`에만 적는다. `apply`는 `pending`도 캐시로 보지만
`changed_files`는 기록(`files`)만 본다. 인덱싱이 끝까지 성공했을 때만 `pending`을
기록으로 옮기고, 인덱싱 조건(`exclude_dirs` 등)도 그때 적는다. 저장은 임시 파일에 다
쓴 뒤 이름을 바꿔 덮어써, 쓰는 도중 끊겨도 반쯤 쓰인 장부가 남지 않는다.

### 잰 것

요금 없이 재려고, 실제 `index_repo`를 부르되 가짜 클라이언트가 100번째 요약 요청에서
Ctrl+C와 같은 `KeyboardInterrupt`를 던지게 했다. 같은 장부로 다시 돌리며 요청 수를 셌다.

| 단계 | 결과 |
|---|---|
| 끊지 않았을 때 | 요청 362번 |
| 100번째에서 끊은 직후 | 장부 기록 0 / pending 27 |
| 다시 돌렸을 때 | 요청 263번(362-99), 캐시 재사용 99개, 장부 기록 79 / pending 0 |

끊긴 직후 기록이 0인 것이 핵심이다. 끝까지 가지 못했으니 인덱스 기록은 하나도
바뀌지 않았고, 27개 파일의 요약은 pending에 살아 있다가 다음 실행에서 그대로 쓰였다.
이번에는 새 파일의 첫 요청에서 끊겨 버려진 요약이 없었다. 파일 한가운데서 끊기면
그 파일에서 이미 한 요약은 저장 전이라 다시 요약한다.

## 요약 병렬화: 파일 안에서만, 동시 4개

어디서 병렬로 돌릴지를 먼저 정했다. 파일 하나의 청크를 동시에 보내면 파일마다
끝내고 저장하는 흐름이 그대로 남는다. 파일을 넘나들면 더 빠르지만 그 흐름을 뜯어야
한다. claim-trace의 실제 파일별 청크 수(79개 파일, 중앙값 3개, 최대 38개)로 요청
하나를 1초로 치고 계산했다.

| 동시 요청 | 파일 안에서만 | 파일을 넘나들며 |
|---|---|---|
| 2개 | 1.8배 | 2.0배 |
| 4개 | 3.0배 | 4.0배 |
| 8개 | 4.0배 | 7.9배 |

동시 요청은 작게 잡아야 한다. Claude API의 분당 한도는 초 단위로 나뉘어 적용될 수
있어 몰아 보내면 한도에 걸리고, 사용 이력이 짧은 조직은 기본보다 낮은 한도에서
시작한다. 요금은 동시성과 무관하게 청크 수만큼 나가므로 빨라지는 것 말고 얻을 것이
없다. 4개라면 파일 안에서만으로도 이론상 최대치의 75%를 얻고, 저장 흐름을 지킨다.

### 잰 것

| 조건 | 순차 | 동시 4개 | 배수 |
|---|---|---|---|
| 가짜(요청당 0.1초), claim-trace 전체 | 38.0초 | 13.0초 | 2.9배 |
| 실제 Haiku, mfds 요약 49개 | 49.6초 | 16.4초 | 3.0배 |

가짜 클라이언트로 계산한 3.0배가 실제 인덱서 흐름에서도 나왔고, 실제 모델에서도
같았다. 실제 실행에서 한도 오류는 없었다. 스레드 네 개가 SDK 클라이언트 하나를 함께
써도 문제가 없었다. 인덱싱 결과(청크, 줄 범위, 파일 요약)는 전후로 같았다.

## 남은 것

- 파일을 넘나드는 병렬화. 동시 4개에서 3.0배가 4.0배가 된다. 저장 흐름을 파일 완료
  순서로 다시 짜야 한다.
- 한도에 닿으면 SDK가 기본으로 두 번 다시 시도하고, 그래도 실패하면 인덱싱이 멈춘다.
  중간 저장 덕분에 그때까지의 요약은 남는다. 한도가 낮은 조직에서 자주 멈춘다면
  동시 요청 수를 설정으로 빼야 한다.
