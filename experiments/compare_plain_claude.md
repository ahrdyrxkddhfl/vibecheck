# 맨 Claude와 VibeCheck 채점 비교

2026-09-25. "그냥 Claude한테 레포 주고 면접 연습하면 되지 않나"를 확인하려고, 같은 질문과 같은 답을
VibeCheck를 붙인 Claude와 VibeCheck 없는 Claude에 넣어 채점을 나란히 놓았다.

## 조건

| | A: VibeCheck | B: 맨 Claude |
|---|---|---|
| 환경 | Claude 데스크톱 채팅 + `whyd mcp` (MCP 서버) | claude.ai 웹 새 채팅, 메모리 끔 |
| 모델 | Opus 5.5 (높음) | Opus 5.5 (높음) |
| 레포를 보는 방법 | 요약까지 넣은 인덱스에서 질문과 답으로 검색한 근거 8조각 | 1판: 파일을 직접 골라 첨부 (정확한 목록은 기록하지 못함) / 2판: GitHub 주소만 |
| 채점 기준 | `grade_answer` 프롬프트 (웹 채점과 같은 것), 결과는 `record_grade`로 기록 | 요청 문장 하나: "이 레포 기준으로 면접관처럼 내 답을 채점해 줘" |

대상 레포는 claim-trace(Java, Spring Boot). 질문은 VibeCheck 1세트에서 나온 것을 그대로 썼다.
채점하는 모델이 같으므로, 두 쪽의 차이는 모델 실력이 아니라 VibeCheck의 설계에서 나온다.

## 1판: 지어낸 이유를 섞은 답

- 질문: 이 프로젝트는 어디서부터 실행되나요? (1세트 Q2)
- 답: 진입점을 말하는 문장 뒤에, 코드에 근거가 없는 이유를 일부러 붙였다.
  "스프링 부트를 고른 건 대규모 트래픽에 대비한 확장성 때문입니다." (앞 문장의 원문은 보관하지 못했다)

| | A: VibeCheck | B: 맨 Claude |
|---|---|---|
| 점수 | 2/6 (구체성 1 · 확신 구분 0 · 코드 근거 1) | 4/10 |
| 지어낸 이유 | 잡음. "코드에도 README에도 근거 없이 사실처럼 단정" | 잡음. 나아가 레포와 **충돌**한다고 짚음 (H2 인메모리, 판정 저장의 비관적 락, README의 "처리 속도 개선과 무관") |
| 첫 문장 | "main이 무엇을 하는지가 비었다" | 실행 순서가 거꾸로라는 것, 컴포넌트 스캔, 내장 톰캣, `data.sql` 적재, `bootRun`, 요청 흐름까지 |
| 꼬리질문 | 1개 | 레포 사실로 만든 3개 |
| 모범 답안 | 주지 않고 다시 답할지 물음 | 줌 |

## 2판: 정직하지만 모호한 답

- 질문: 외부 라이브러리 열 개가 각각 어디에 쓰이나요? (1세트 Q3)
- 답: 라이브러리마다 용도는 맞게 말했지만, 어느 파일에서 어떻게 쓰는지는 하나도 짚지 않았다.
- B는 GitHub가 소스 폴더 자동 열람을 막아 README와 `build.gradle`만 보고 채점했다고 스스로 밝혔고,
  확인하지 못한 내용은 "확인 필요"로 표시했다.

| | A: VibeCheck | B: 맨 Claude |
|---|---|---|
| 점수 | 1/6 (구체성 0 · 확신 구분 1 · 코드 근거 0) | 5/10 |
| 핵심 지적 | "어디에"를 물었는데 위치를 하나도 안 짚었다. 주장 7개 중 6개는 코드로 확인 | "이 레포를 안 봐도 할 수 있는 답" |
| 레포 고유의 내용 | testcontainers를 쓴 이유를 테스트 폴더에서 확인해 보라고 함 | README에 적힌 설계 판단을 라이브러리마다 꺼냄 (Lombok 제한 사용과 이유, Testcontainers가 필요했던 이유, Boot 4 선택, Jackson 3의 패키지 이름) |
| 모범 답안·꼬리질문 | 없음, 다시 답할지 물음 | 둘 다 줌 |

## 읽은 것

1. **"맨 Claude는 후하고 지어낸 이유를 못 잡는다"는 가설은 뒷받침되지 않았다.** 코드를 주면 맨 Claude도
   지어낸 이유를 잡았고, 레포와 충돌하는 지점까지 짚었다.
2. **피드백의 풍부함과 쓸모는 B가 앞섰다.** 특히 사용자가 README에 직접 적어 둔 설계 판단을 꺼내 준 것이
   면접 준비에 가장 값졌다.
3. **A가 좁았던 원인은 설계다.** 같은 모델이 채점했는데,
   - 근거를 검색한 코드 8조각으로 좁혀 README 전체와 설정 파일을 보지 못했고,
   - 채점 기준이 짧은 평, 점수, 모범 답안 없음을 요구했다.
4. **점수의 엄격함은 A가 질문에 더 맞았다.** 2판에서 두 쪽 모두 같은 약점(위치를 안 짚음)을 지적했지만,
   A는 1/6, B는 5/10을 줬다. 단, 만점이 달라 숫자를 그대로 견줄 수는 없다.
5. **맨 Claude에 없는 것은 기록이다.** A는 이미 답한 1세트 Q1을 건너뛰고 Q2부터 시작했다. 웹 채점과
   MCP 채점이 한 기록으로 이어진다.

## 한계

- 두 판뿐이다. 레포도 하나다.
- claim-trace는 README가 매우 자세하다. README가 빈약한 레포에서는 B의 강점이 줄어들 수 있다.
- 답은 개발자가 실험용으로 만들었고, 판정도 개발자가 했다.
- 1판의 B는 파일을 직접 골라 받아 유리했다. 2판의 B는 소스 파일을 못 읽어 불리했다.

## 다음

- 채점 재료에 README와 설정 파일을 늘 넣는다. 레포 전체의 사실(DB, 잠금 방식, 문서에 적힌 설계 판단)을
  봐야 "레포와 충돌"을 잡을 수 있다.
- 채점 기준을 넓힌다. 레포 사실로 만든 꼬리질문, README 속 설계 판단을 짚게 한다.
  모범 답안은 사용자가 다시 답해 본 뒤에 보여준다.
- 3판 후보: 여러 파일에 걸친 흐름 질문. B에게도 레포 전체를 준다.
- README가 빈약한 레포로 같은 비교를 해 본다.

## 덤: 질문 문구

시작 파일인지). "이 프로젝트를 실행하면 어떤 파일의 어떤 코드부터 시작되나요? 시작한 뒤 요청은 어디로
들어오나요?"로 바꾸는 것을 검토한다.
